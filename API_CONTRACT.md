- **Instance**: `http://localhost/bugzilla`
- **REST base**: `http://localhost/bugzilla/rest`

## 1. Authentication

Bugzilla REST accepts the API key three ways; this project standardizes on the query-param form server-side (BFF-only, never exposed to the browser):

```
GET /rest/bug/1?api_key=<KEY>
```

Equivalently supported (not used, documented for completeness): `X-Bugzilla-API-Key` header, or `login`+`password` params via `GET/POST /rest/login`.

### Auth error shapes

| Condition | HTTP | Body |
|---|---|---|
| Invalid/garbage API key | 400 | `{"error":true,"code":306,"message":"The API key you specified is invalid. Please check that you typed it correctly."}` |
| No auth, resource requires login | 401 | `{"error":true,"code":102,"message":"You are not authorized to access bug #2. To see this bug, you must first log in to an account with the appropriate permissions."}` |
| `login`/`password` invalid on `/login` | 200 (!) | `{"error":true,"code":300,"message":"The login or password you entered is not valid."}` — note: this endpoint returns HTTP 200 even on failure; only the JSON body's `error:true` signals failure. BFF must check body, not just status. |
| `match` param on `/user` while logged out | 401 | `{"error":true,"code":505,"message":"Logged-out users cannot use the \"match\" argument..."}` |

**Note on API keys**: Bugzilla 5.2 has no REST endpoint to *generate* an API key — it must be created via the web UI (Preferences → API Keys), which is intentionally protected by a JS-populated CSRF token that cannot be scripted. The key used throughout this contract was generated manually in-browser by the project owner.

## 2. `GET /version`

```json
{"version":"5.2"}
```
No auth required. Also returns standard security headers on every response: `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection: 1; mode=block`, `Access-Control-Allow-Origin: *`, and sets an `Bugzilla_login_request_cookie` (irrelevant to REST auth, safe to ignore/drop).

## 3. `GET /field/bug` — field metadata

Returns `{"fields": [...]}`, 59 fields on this instance. Key excerpt (`is_mandatory` and enum `values` per field):

| Field | `is_mandatory` | Notes |
|---|---|---|
| `short_desc` (Summary) | **true** | free text |
| `product` | **true** | enum, drives visibility of `component`/`version`/`target_milestone` via `value_field` |
| `component` | **true** (metadata says true, and enforced) | enum, `value_field: "product"` |
| `version` | **true** (metadata) | enum, `value_field: "product"`; every product on this instance has an `"unspecified"` (or `"1.0"` for KSMACC) version |
| `op_sys` | metadata says `false`, **but enforced as required at creation time** (see §7) | enum: `All, Windows, Mac OS, Linux, Other` |
| `platform` (rep_platform) | metadata says `false`, **but enforced as required at creation time** | not enumerated in the excerpt above but behaves identically to `op_sys` — always send `"All"` |
| `bug_status` | false | enum with full state machine, see below |
| `resolution` | false | enum: `"", FIXED, INVALID, WONTFIX, DUPLICATE, WORKSFORME` |
| `bug_severity` | false | enum: `blocker, critical, major, normal, minor, trivial, enhancement` |
| `priority` | false | enum: `Highest, High, Normal, Low, Lowest, ---` |
| `target_milestone` | false | per-product, all currently `"---"` only |

⚠️ **Important deviation from Bugzilla defaults**: this instance requires `op_sys` and `platform` to be explicitly supplied on `POST /bug` (confirmed empirically — omitting either yields `400 {"code":50,"message":"You must select/enter a OS."}`). The BFF must always default these to `"All"` when the client doesn't override, exactly as the brief specifies.

### `bug_status` state machine (from `field/bug`, condensed)

| From | Can change to |
|---|---|
| *(new bug, no status yet)* | UNCONFIRMED, CONFIRMED, IN_PROGRESS |
| UNCONFIRMED | CONFIRMED, IN_PROGRESS, RESOLVED |
| CONFIRMED | IN_PROGRESS, RESOLVED |
| IN_PROGRESS | CONFIRMED, RESOLVED |
| RESOLVED | UNCONFIRMED, CONFIRMED, VERIFIED |
| VERIFIED | UNCONFIRMED, CONFIRMED |

`is_open`: true for UNCONFIRMED/CONFIRMED/IN_PROGRESS, false for RESOLVED/VERIFIED.

Invalid status/severity/resolution names produce `404 {"code":51,"message":"There is no <Field> named '<value>'."}` — a client-input error despite the 404 status; BFF should normalize this to a 400 in its typed error contract.

## 4. `GET /product`, `GET /product_accessible`, `GET /product_enterable`

`GET /product` **requires** one of `ids`, `names`, or `type` — bare `GET /product` returns `400 {"code":50,"message":"...requires that you set one of the following parameters: ids, names, type"}`.

Working pattern (2-step, as Bugzilla intends):

```
GET /rest/product_accessible?api_key=...   →  {"ids":[2,4,3,1]}
GET /rest/product?ids=1&ids=2&ids=3&ids=4&api_key=...  →  full product objects
```

`product_enterable` behaves identically to `product_accessible` on this instance (same 4 ids) — use `product_enterable` for "Create Bug" product dropdown since it specifically means "can file bugs into this product."

Each component object includes `default_assigned_to` (email string) — useful for pre-filling assignee in the Create Bug form.

## 5. `GET /bug` — search & pagination

- No `total_matches`/`X-Total-Count` in headers or body — **Bugzilla REST does not return a total count**. Pagination must be done by fetching `limit+1` or by detecting `bugs.length < limit` as the "last page" signal, OR issuing a second lightweight count query with `include_fields=id` only.
- Response shape: `{"bugs": [ {...full bug object...}, ... ]}`
- Unknown/bogus query params are **silently ignored**, not rejected (tested `totally_bogus_param=xyz` → 200, default list returned). BFF should not rely on Bugzilla to validate its own query params.

### Confirmed working filter/sort params

| Param | Behavior | Example |
|---|---|---|
| `limit`, `offset` | standard pagination | `?limit=5&offset=0` |
| `product` | exact match | `?product=KSMACC` |
| `bug_status` **or** `status` | exact match on status name (both aliases work identically) | `?bug_status=CONFIRMED` → 36 results |
| `severity` | exact match | `?severity=normal` → 23 results |
| `assigned_to` | exact match on email | `?assigned_to=mani@gmail.com` |
| `order` | sort field (e.g. `priority`) | `?order=priority` |
| `summary` | **substring match** (not exact) | `?summary=mobile` matched 5 bugs with "mobile" anywhere in summary, case-insensitive |
| `quicksearch` | Bugzilla's quicksearch syntax; broader boolean/keyword matching than `summary` | `?quicksearch=mobile` matched 13 bugs (also matched "mobileNoExist", "mobileNumber" tokens inside longer summaries) |

**Recommendation for BFF**: use `bug_status`, `severity`, `priority`, `product`, `component`, `assigned_to` for the filter bar's dropdowns (exact match), and `summary` (substring) for the free-text global search box — cheaper and more predictable than `quicksearch` for a table UI.

## 6. `GET /bug/{id}` — single bug detail

Response shape differs slightly from the list: `{"bugs": [ {...} ], "faults": []}` (array of one, plus a `faults` array for batch-lookup error reporting — empty on single-id success). When authenticated, the bug object additionally includes an `update_token` field (legacy web-UI CSRF token; **not required** for REST `PUT`, which authenticates via `api_key` — safe to ignore/drop in the BFF's normalized response).

- `GET /bug/999999` (nonexistent) → `404 {"code":101,"message":"Bug #999999 does not exist."}`
- `GET /bug/{id}` for a bug in a restricted group, no/insufficient auth → `401 {"code":102,"message":"...you must first log in..."}`
- A public bug (no group restriction) is readable **without** `api_key` at all — Bugzilla REST allows fully anonymous reads where Bugzilla's own permission model allows it. The BFF should always attach its own `api_key` server-side regardless, so behavior is consistent for all users of the SaaS UI (the UI's own login is separate — see §9).

## 7. `GET /bug/{id}/comment`, `GET /bug/{id}/attachment`, `GET /bug/attachment/{id}`

### Comments
```
GET /bug/1/comment
→ {"comments": {}, "bugs": {"1": {"comments": [ {id, count, text, creator, creation_time, time, is_private, attachment_id, tags, bug_id}, ... ]}}}
```
Note the **object-keyed-by-bug-id** shape (`bugs["1"]`), unlike the array shape used by `GET /bug`. `count` is the 0-indexed comment position (comment 0 = the original bug description). Comments created via attachment upload appear inline with `attachment_id` set and auto-generated text like `"Created attachment 1\nlogin-bug.png"`.

### Attachments (list, includes base64 data inline)
```
GET /bug/1/attachment
→ {"attachments": {}, "bugs": {"1": [ {id, bug_id, file_name, summary, content_type, size, is_patch, is_obsolete, is_private, creator, creation_time, last_change_time, data, flags}, ... ]}}
```
`data` is base64-encoded file content, returned **inline** — for a 339,576-byte PNG this made the JSON payload large. **BFF recommendation**: expose a separate `GET /api/bugs/:id/attachments/:attachmentId/download` route that fetches+decodes+streams binary with correct `Content-Type`/`Content-Disposition`, rather than shipping base64 JSON to the browser for anything but small previews.

### Single attachment by attachment id
```
GET /bug/attachment/{attachment_id}
→ {"attachments": {"<id>": {...same fields as above...}}, "bugs": {}}
```

## 8. Write operations (tested against a live throwaway bug)

**Throwaway bug created: `bug_id 38`** in `TestProduct` / `TestComponent`, summary `"ZZZ_THROWAWAY_DISCOVERY_BUG_DELETE_ME - Phase 0 API probe"`. Please delete/mark INVALID after review — not otherwise cleaned up automatically per the constraint against unrequested destructive actions.

### `POST /bug` — create

Request:
```json
{
  "product": "TestProduct",
  "component": "TestComponent",
  "summary": "ZZZ_THROWAWAY_DISCOVERY_BUG_DELETE_ME - Phase 0 API probe",
  "version": "unspecified",
  "description": "This is a throwaway bug created by automated API discovery. Safe to delete.",
  "op_sys": "All",
  "platform": "All",
  "severity": "minor",
  "priority": "Low"
}
```
Response: `200 {"id": 38}` — note: only the new id is returned, **not** the full bug object. BFF's `POST /api/bugs` should chain a `GET /bug/{id}` to return the full normalized bug to the frontend (needed for the "redirect to new bug detail" UX in the brief).

Default status on creation (this instance): `CONFIRMED` (not `UNCONFIRMED`) — likely because the authenticated admin user has `editbugs`/`canconfirm`. A less-privileged user might default differently; the BFF shouldn't hardcode an assumption here.

### `POST /bug/{id}/comment` — add comment

Request: `{"comment": "Throwaway discovery comment - safe to ignore.", "is_private": false}`
Response: `201 {"id": 110}` (the new *comment's* global id, not bug-scoped).

### `PUT /bug/{id}` — update

Request: `{"priority": "Highest", "status": "CONFIRMED"}`
Response: `200 {"bugs": [{"id":38,"alias":[],"last_change_time":"...","changes":{"priority":{"removed":"Low","added":"Highest"}}}]}`
Note: `changes` only lists fields that **actually changed** — `status` was already `CONFIRMED` so it's silently omitted from `changes`, not an error. BFF should treat `PUT` as idempotent-safe: sending a no-op field is fine.

### `POST /bug/{id}/attachment` — add attachment

Request: `{"ids":[38],"data":"<base64>","file_name":"discovery-note.txt","summary":"Throwaway discovery attachment","content_type":"text/plain"}`
Response: `201 {"ids":[37]}` (attachment id, own sequence separate from bug/comment ids).

### Create-bug validation error catalog (all tested live)

| Scenario | HTTP | Body |
|---|---|---|
| Missing `component` | 400 | `{"code":105,"message":"To file this bug, you must first choose a component. If necessary, just guess."}` |
| Missing `summary` | 400 | `{"code":107,"message":"You must enter a summary for this bug."}` |
| Missing/omitted `op_sys` or `platform` | 400 | `{"code":50,"message":"You must select/enter a OS."}` |
| Nonexistent `product` | **401** (not 400/404) | `{"code":106,"message":"Sorry, either the product NoSuchProduct does not exist or you aren't authorized to enter a bug into it."}` — deliberately ambiguous between "doesn't exist" and "no permission," by Bugzilla design |
| Invalid enum value (e.g. `severity:"catastrophic"`) | 404 | `{"code":51,"message":"There is no Severity named 'catastrophic'."}` |
| Invalid `status` value on `PUT` | 404 | `{"code":51,"message":"There is no status named 'NOT_A_REAL_STATUS'."}` |

**BFF error-normalization rule**: Bugzilla mixes 400/401/404 somewhat inconsistently for what are all really "400 Bad Request" client input problems (codes 50/51/105/106/107 are all validation-class errors regardless of HTTP status). The typed error contract should classify by Bugzilla's numeric `code`, not by raw HTTP status, and present a uniform `{status: 400, code, message}` shape to the frontend.

## 9. `GET /user` — lookups

- `GET /user?match=<substring>` — requires auth; returns matching users (`id`, `name`/email, `real_name`, `email`, `groups`, `can_login`). Anonymous access → `401 {"code":505}`.
- `GET /user/{id}` — direct lookup by id, requires auth for full detail (includes `saved_searches`, `saved_reports`, `groups`).
- No REST endpoint exists to create/rotate API keys (see §1 note) or to log in and receive a long-lived API key — `POST /login` returns a short-lived session `token`, not an API key.

**Auth strategy for Phase 2 "Login" screen**: since there's no per-end-user API key provisioning via REST, and the brief mandates the API key stay server-side, the SaaS app's own login should authenticate the *end user* against Bugzilla via `POST /login` (`login`+`password` → `{id, token}`), store that in the BFF's signed session cookie, and use the **admin service API key** for all actual Bugzilla REST calls (a service-account pattern) OR pass the logged-in user's own token through per-request if per-user permission fidelity (e.g., respecting individual group restrictions) is required. Given product `4` (KPost API) is group-restricted, **per-user token pass-through is recommended** over a single shared service API key, so that group permissions in Bugzilla are respected per logged-in user rather than flattened to the admin's view. This should be confirmed with you before Phase 1 implementation.

## 10. Cross-cutting notes for the BFF

- **Timeouts**: no server-side slowness observed (all probes <300ms locally), but the brief's 15s upstream timeout is still the right defensive default.
- **CORS**: Bugzilla itself already sends permissive CORS headers, irrelevant once proxied through the BFF (frontend never calls Bugzilla directly).
- **Content-Type**: Bugzilla REST responds `application/json; charset=UTF-8` uniformly, including on errors.
- **Zod modeling implication**: because Bugzilla is schema-flexible (custom fields, per-product enum visibility via `visibility_values`), the BFF's Zod schemas should use `.passthrough()` or an explicit allowlist per view rather than `.strict()`, to avoid breaking on fields introduced by future product/component config changes in Bugzilla admin.

## 12. Admin discovery (live-probed, 2026-08-13) — Users, Products, Components

Probed against the same instance to determine exactly which admin operations are safe to build over REST, ahead of the glassmorphism + admin-features extension. Every endpoint below was actually called; nothing here is assumed from memory.

### 12.1 Users

| Operation | Endpoint | Requires | Notes |
|---|---|---|---|
| Search/list | `GET /user?match=<substring>` | Any logged-in user | Works for **any** authenticated user, not just admins — but returns **redacted** data for other users (e.g. `groups: []`) unless the caller has `editusers`. The Users *page* should still be gated on `editusers` per the brief, even though this specific read technically doesn't require it. |
| Self-lookup | `GET /user/{ownId}` | Any logged-in user | Returns the caller's **own full group list** regardless of privilege — this is how the BFF computes the current user's admin capabilities right after login (no separate "whoami" endpoint exists; `GET /user/self` is invalid — must use the numeric id returned by `/login`). |

### 12.4 Permission-denial shape (uniform across all three)

Every privilege check above returns the **same shape** regardless of resource — confirmed both fully-anonymous and, more importantly, **while authenticated as a genuine non-privileged user** (a throwaway account with no `editusers`/`editcomponents` membership, logged in normally via `/login`, tested against `POST /user`, `POST /product`, and `POST /component`):

```json
{
  "error": true,
  "code": 304,
  "message": "Sorry, you aren't a member of the 'editusers' group, and so you are not authorized to add new users."
}
```
HTTP status is **401**, not 403, even though the caller is fully authenticated — Bugzilla conflates "not authenticated" and "authenticated but not privileged enough" under the same status code here (code `304` is the reliable discriminator, not the HTTP status). The BFF's existing `mapBugzillaError` needs a new case for `304` → a distinct `FORBIDDEN`-style code so the frontend can render "you don't have permission" rather than bouncing the user to the login screen (which is what a generic 401→`UNAUTHENTICATED` mapping would currently do).

Ordinary reads (`GET /bug`, `GET /product_enterable`) were confirmed to work normally for the same non-privileged test account — only the admin *write* operations are gated, so the rest of the app is unaffected for non-admin users.

### 12.5 Group/permission administration — deliberately not probed further

Bugzilla's REST API almost certainly exposes some form of group-membership editing on `PUT /user/{id}` (a structured `groups: {add:[...], remove:[...]}` field, by convention in other Bugzilla webservice methods), but per the Part D boundary this project is drawing, we did not probe or document it further — group/permission administration stays exclusively in Bugzilla's native `editusers.cgi` / `editgroups.cgi`, linked out to from an "Advanced Administration" panel instead of being reimplemented here.

## 13. BFF endpoints (this app's own API, added with the two-axis classification)

Everything above documents *Bugzilla's* REST API. This section documents the
endpoints **this BFF** exposes to its frontend. All require an authenticated
session (`middleware/auth.ts`) and use the user's own Bugzilla token, so results
respect Bugzilla's per-user group visibility.

### 13.1 The classification model

Two axes. Severity and Priority are paired; Category is independent.

| Severity | Priority | Meaning |
|---|---|---|
| Critical | P0 / Showstopper | Crash, severe data loss, total feature blockade, no workaround |
| Major | P1 | Significant loss of core functionality; difficult workaround may exist |
| Minor | P2 | Small functional failure or limitation |
| Trivial | P3 | Cosmetic — misalignment, spelling, visual glitch |

Category: `Functional` · `Performance` · `Security` · `Compatibility`.

Anything unmapped degrades to an explicit **`Unclassified`** bucket on every
axis — never dropped, never fatal to a request.

### 13.2 How the axes are encoded in Bugzilla (probed live, 2026-08-19)

Bugzilla has native fields for severity and priority and **nothing for
category**, so two encodings coexist and both are read:

| Axis | Current bench writes | The 1,283 pre-change bugs hold |
|---|---|---|
| Category | `[cat:Security]` — the only tag on the Status Whiteboard | *nothing* — whiteboard is only the legacy `[tierN]` (now ignored), `keywords` empty on every bug |
| Severity | `critical` / `major` / `minor` / `trivial` | `critical` 130, `major` 706, **`normal` 187**, `minor` 260 |
| Grouping | `Affected endpoints (N), observed by M test case(s):` block in the description | *absent* — 0 descriptions carry it |

Legacy bugs stay classifiable because **all 1,283 carry a `Classification:`
line** as the first line of their description, which maps to a category through
the same table the bench uses (`CATEGORY_BY_CLASSIFICATION`).

`minor` is overloaded — the old bench used it for the P3 band, the new one for
P2 — and is resolved by its paired priority (`minor`+`Low` → Trivial,
`minor`+`Normal` → Minor). Severity and priority pair 1:1 in the data, which is
what makes this exact.

**All of this lives in `backend/src/lib/classification.ts`.** Parsing and
filtering both read from it; no classification string literal belongs anywhere
else.

### 13.3 Verified Bugzilla query primitives

Counts below are exact against the live instance:

| Query | Result |
|---|---|
| `bug_severity=critical&bug_severity=major` (repeat = OR) | 836 = 130 + 706 |
| repeat OR + second axis (AND) | 17 |
| `longdesc=Security/` (description substring search) | 338 = 314 + 13 + 11 |
| boolean chart `f1=status_whiteboard` OR `f2=longdesc`, `j_top=OR` | 338 |
| that chart AND `bug_severity=critical` | 17 |

The boolean chart is what lets one category filter match **either** encoding in
a single Bugzilla query — no fetch-and-filter in the BFF.

### 13.4 `GET /api/bugs`

Filters, all combinable. Repeating a key ORs within that axis; separate keys AND
across axes. Invalid enum values are rejected with `400 VALIDATION` through the
existing `parseInput`/`errorHandler` path — nothing unvalidated reaches Bugzilla.

| Param | Repeatable | Values |
|---|---|---|
| `severity` | yes | `Critical` `Major` `Minor` `Trivial` `Unclassified` |
| `priority` | yes | `P0` `P1` `P2` `P3` `Unclassified` |
| `category` | yes | `Functional` `Performance` `Security` `Compatibility` `Unclassified` |
| `product` / `component` / `status` | yes | free text (Bugzilla's own values) |
| `search` | no | substring against summary |
| `assignedTo` / `creator` / `cc` | no | email |
| `limit` (≤200) / `offset` / `sortBy` / `sortDir` | no | pagination and sort |

Each returned bug gains a **`triage`** object (`severity`, `priority`,
`category`, `classification`). Named `triage`, not `classification`,
because `bug.classification` is already Bugzilla's product-classification string.

### 13.5 `GET /api/bugs/:id`

As above plus `grouping`, parsed server-side from the description so the
frontend never regexes a body:

```json
{ "occurrences": 37, "endpointCount": 12, "truncated": true, "isGrouped": true,
  "affectedEndpoints": [{ "method": "GET", "path": "/v2/a", "module": "Authentication V2", "occurrences": 4 }] }
```

A bug filed before grouping existed returns an explicit empty shape
(`isGrouped: false`, `occurrences: null`, `affectedEndpoints: []`) — never a
partial one.

### 13.6 `GET /api/bugs/stats`

Every dashboard and report breakdown in one call: `total`, `open`, `resolved`,
`bySeverity`, `byCategory`, `byComponent`, and the `matrix` (severity ×
category). Accepts the same filters as the list.

Cost is **five upstream calls on a cold cache, one when warm** — one search
returning four fields per bug, plus one id-set query per category. Not sixteen:
the matrix is computed by joining those in memory rather than querying per cell.
The category id-sets are cached per user for `STATS_CACHE_TTL_MS`
(`config/env.ts`, default 60s) — per user because bugs can be group-restricted
and a shared cache would leak restricted bugs through counts.

### 13.7 `GET /api/bugs/count`

`{ counts: { total, open, resolved, blockerCritical, byStatus, bySeverity } }`
for the same filter set. Used for the result count and the "hidden by filters"
figure in the filter bar.
